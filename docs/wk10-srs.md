## 1. Introduction (บทนำและขอบเขต)

### 1.1 ระบบทำอะไร

Pad-Krapow-cafe-system เป็นระบบขายหน้าร้าน (POS) แบบเว็บสำหรับร้านกาแฟขนาดเล็ก ใช้งานผ่านเบราว์เซอร์บนแท็บเล็ตหรือคอมพิวเตอร์ที่ร้านมีอยู่แล้ว ระบบช่วยให้พนักงานรับออเดอร์ คำนวณยอดเงิน บันทึกวิธีชำระเงิน ตัดสต็อกอัตโนมัติ และแจ้งเตือนเมื่อสินค้าใกล้หมด ส่วนเจ้าของร้านดูรายงานยอดขายรายวันและรายเดือนได้ทันทีโดยไม่ต้องนับจากสมุดปลายวัน

ปัญหาเดิมที่ระบบแก้ (จากการสัมภาษณ์ใน wk03):

| ปัญหาเดิม | สิ่งที่ระบบทำ |
|---|---|
| จดออเดอร์และคิดเงินด้วยมือ ผิดบ่อยช่วงเร่งด่วน | เลือกเมนูจากหน้าจอ ระบบคิดยอดรวมให้ และคิดซ้ำที่ server จากราคาในฐานข้อมูล |
| นมหมดโดยไม่รู้ตัว ต้องปฏิเสธลูกค้ากะทันหัน | แสดงสต็อกคงเหลือบนการ์ดเมนู แจ้งเตือนเมื่อต่ำกว่าขั้นต่ำ และห้ามขายเกินสต็อก |
| ไม่รู้ว่าเมนูไหนขายดี | รายงานยอดขายแยกตามเมนู และเมนูขายดี 5 อันดับแรกของเดือน |

### 1.2 ขอบเขตที่ครอบคลุม (In-Scope)

1. เข้าสู่ระบบด้วยชื่อผู้ใช้และรหัสผ่าน แยกบทบาทบาริสต้ากับเจ้าของร้าน
2. รับออเดอร์: เลือกเมนูตามหมวดหมู่/ค้นหา ปรับจำนวน ลบรายการ เลือกวิธีชำระเงิน และยืนยัน
3. ตัดสต็อกอัตโนมัติเมื่อยืนยันการขาย พร้อมเก็บประวัติการเคลื่อนไหวของสต็อก
4. แจ้งเตือนเมนูที่สต็อกต่ำกว่าจำนวนขั้นต่ำ
5. แสดงใบเสร็จหลังยืนยันออเดอร์ พิมพ์ได้ และเปิดดูย้อนหลังได้
6. จัดการเมนู (เพิ่ม แก้ไข ซ่อน) และเติม/ปรับสต็อก
7. รายงานยอดขายรายวัน/ช่วงวันที่ และรายเดือน
8. รองรับหลายสาขาในฐานข้อมูลชุดเดียว (แยกด้วย `branch_id`) และมีตัวเลือกสาขาในทุกหน้าจอ

### 1.3 ขอบเขตที่ไม่ครอบคลุม (Out-of-Scope)

1. ระบบบัญชีและภาษีเต็มรูปแบบ (ใบกำกับภาษีเต็มรูป, ยื่นภาษี)
2. การสั่งซื้อวัตถุดิบจากซัพพลายเออร์อัตโนมัติ (ระบบแจ้งเตือนเท่านั้น)
3. ระบบสมาชิก/สะสมแต้มลูกค้า (ช่องค้นหาลูกค้าใน wireframe ไม่ได้ทำในเวอร์ชันนี้)
4. ตัวเลือกปรับแต่งเครื่องดื่ม (ความหวาน ท็อปปิ้ง) และส่วนลด
5. การยกเลิก/คืนเงินออเดอร์ที่ยืนยันแล้ว
6. การเชื่อมต่อเครื่องรับบัตรเครดิตหรือ QR แบบอัตโนมัติ (ระบบบันทึกแค่วิธีที่ลูกค้าจ่าย)
7. การทำงานแบบ offline เมื่ออินเทอร์เน็ตหลุด (ดูข้อ 2.2 ข้อจำกัด)
8. สูตรวัตถุดิบต่อเมนู (เช่น 1 แก้วใช้นม 200 ml) — สต็อกนับเป็น "จำนวนที่ขายได้ต่อเมนู"

## 2. Overall Description (ภาพรวมของระบบ)

### 2.1 กลุ่มผู้ใช้งาน (Roles & Responsibilities)

| บทบาท | ใช้ระบบหรือไม่ | สิ่งที่ทำได้ในระบบ |
|---|---|---|
| ลูกค้า (Customer) | ไม่ใช้โดยตรง | แจ้งเมนูกับพนักงาน ชำระเงิน และรับใบเสร็จ |
| บาริสต้า (`barista`) | ใช้ | รับออเดอร์, ดูใบเสร็จ, ดูเมนูและสต็อก, เติม/ปรับสต็อก, ดูรายงานของ **สาขาตัวเองเท่านั้น** |
| เจ้าของร้าน (`owner`) | ใช้ | ทุกอย่างของบาริสต้า **ในทุกสาขา** + เพิ่ม/แก้ไข/ซ่อนเมนู |

ตารางสิทธิ์แยกตามฟังก์ชัน:

| ฟังก์ชัน | barista | owner |
|---|:---:|:---:|
| รับออเดอร์ / ดูใบเสร็จ | ✓ (สาขาตัวเอง) | ✓ (ทุกสาขา) |
| ดูเมนูและสต็อก / เติม-ปรับสต็อก | ✓ (สาขาตัวเอง) | ✓ |
| เพิ่ม / แก้ไข / ซ่อนเมนู | ✗ | ✓ |
| รายงานรายวันและรายเดือน | ✓ (สาขาตัวเอง) | ✓ |
| เปลี่ยนสาขาในตัวเลือกด้านบน | ✗ (ล็อกไว้) | ✓ |

> หมายเหตุ: US-07/US-08 ระบุผู้ใช้รายงานเป็นเจ้าของร้าน แต่ Task 3 ใน Usability Testing (wk12) ให้พนักงานดูเมนูขายดีของวัน จึงเปิดให้บาริสต้าดูรายงานของสาขาตัวเองได้ด้วย

### 2.2 ข้อจำกัดและสมมติฐาน (Constraints & Assumptions)

**ข้อจำกัด**

- C-01 ใช้ฮาร์ดแวร์ที่ร้านมีอยู่: แท็บเล็ต 1 เครื่อง และคอมพิวเตอร์ตั้งโต๊ะ 1 เครื่อง ไม่ลงทุนอุปกรณ์เฉพาะทาง
- C-02 งบประมาณจำกัด ใช้ซอฟต์แวร์ฟรี: Node.js, Express, MySQL Community / MariaDB
- C-03 พนักงานไม่มีพื้นฐาน IT เชิงลึก UI ต้องเรียบง่าย ปุ่มใหญ่ ใช้นิ้วแตะได้
- C-04 ต้องใช้งานได้ภายใน 2–3 เดือน
- C-05 ระบบต้องเชื่อมต่อ server ตลอดเวลา ถ้า WiFi หลุด หน้าจอจะแจ้ง "เชื่อมต่อเซิร์ฟเวอร์ไม่ได้" และไม่บันทึกออเดอร์ (ยังไม่รองรับ offline ตามที่ wk03 ระบุว่า "ควรรองรับเบื้องต้น" — ยกไปเป็นงานในอนาคต)

**สมมติฐาน**

- A-01 Server และฐานข้อมูลติดตั้งบนคอมพิวเตอร์หลังร้าน แท็บเล็ตเข้าผ่าน WiFi ของร้าน (ดู Physical View ใน wk11)
- A-02 "สต็อกวัตถุดิบ" ใน FR-04/05/08 ใช้ความหมายว่า **จำนวนแก้ว/ชิ้นที่ยังขายได้ของแต่ละเมนู** (`menu_item.stock_quantity`) ตาม ER Diagram wk07 ไม่ได้แยกวัตถุดิบเป็นรายการย่อย
- A-03 เวลาทั้งหมดในระบบเป็นเวลาประเทศไทย (UTC+7)
- A-04 ราคาที่บันทึกใน `order_item.unit_price` คือราคา ณ เวลาขาย ถ้าแก้ราคาเมนูภายหลัง ยอดขายเก่าในรายงานไม่เปลี่ยน

## 3. Specific Requirements (ความต้องการของระบบ)

### 3.1 Functional Requirements (FR)

| รหัส | Requirement | User Story | วิธีที่ระบบทำ (Implementation) | Test |
|---|---|---|---|---|
| FR-01 | บันทึกรายการสั่งซื้อ ระบุเมนูและจำนวนต่อออเดอร์ | US-01, US-03 | หน้า POS แตะการ์ดเพื่อเพิ่ม ปุ่ม −/+ หรือพิมพ์จำนวน ลบรายการได้ `POST /api/orders` รวมเมนูซ้ำให้อัตโนมัติ | TC-10, TC-12, TC-16 |
| FR-02 | คำนวณยอดเงินรวมอัตโนมัติ | US-02 | หน้าจอคำนวณทันทีที่ตะกร้าเปลี่ยน และ server คำนวณซ้ำด้วย `Order.calculateTotal()` จากราคาในฐานข้อมูล บันทึกใน `orders.total_amount` | TC-10, TC-13, unit tests |
| FR-03 | บันทึกช่องทางชำระเงิน (เงินสด / โอน / QR พร้อมเพย์) | US-04 | ปุ่มเลือก 3 แบบ ต้องเลือกก่อนยืนยัน server รับเฉพาะ `cash`, `transfer`, `promptpay` และมี CHECK ในฐานข้อมูล | TC-11 |
| FR-04 | ตัดสต็อกอัตโนมัติเมื่อยืนยันขาย | US-05 | ตัดสต็อกใน transaction เดียวกับการบันทึกออเดอร์ ล็อกแถวด้วย `SELECT ... FOR UPDATE` ถ้าสต็อกไม่พอจะ rollback ทั้งออเดอร์ และบันทึก `stock_movement` (reason = `sale`) ทุกครั้ง | TC-10, TC-15, TC-20 |

| FR-07 | สรุปยอดขายรายเดือน แสดงยอดรวมและเมนูขายดี 5 อันดับแรก | US-08 | แท็บ "รายเดือน" กราฟแท่งยอดขายรายวัน + ตาราง Top 5 `GET /api/reports/monthly` | TC-42 |
| FR-08 | แสดงสต็อกคงเหลือแบบเรียลไทม์บนแท็บเล็ต | US-05, US-06 | หน้า POS ดึงข้อมูลเมนูใหม่ทุก 3 วินาที (เมื่อแท็บเปิดอยู่) และหลังทุกออเดอร์ | ทดสอบด้วยมือ (E2E-07) |
| FR-09 | ใช้งานผ่านหน้าจอแท็บเล็ตโดยไม่ต้องติดตั้งเพิ่ม | — | เว็บแอป responsive ปุ่มสูงอย่างน้อย 44px ทดสอบที่ความกว้าง 1280px และ 390px | E2E-08 |

### 3.2 Non-Functional Requirements (NFR)

| รหัส | Requirement | วิธีที่ระบบทำ / วิธีวัด | สถานะ |
|---|---|---|---|
| NFR-01 | บันทึกออเดอร์และคำนวณยอดเสร็จภายใน 2 วินาที | transaction เดียว query ตาม primary key และมี index `(branch_id, created_at)` วัดจริง 10 ครั้งผ่าน HTTP บนเครื่องทดสอบ (MySQL 8.0 มีออเดอร์ในฐานข้อมูล ~900 รายการ): ค่ากลาง 8 ms ช้าสุด 22 ms | ผ่าน (วัดบนเครื่องพัฒนา ควรวัดซ้ำบนเครื่องจริงของร้าน) |
| NFR-02 | พนักงานใหม่บันทึกออเดอร์แรกได้ภายใน 5 นาทีหลังอบรม | UI 3 ขั้น: แตะเมนู → เลือกวิธีจ่าย → ยืนยัน ปุ่มยืนยันบอกว่ายังขาดอะไร | ต้องวัดจริงใน Usability Test รอบถัดไป (wk12) |
| NFR-03 | เข้ารหัสรหัสผ่านด้วย bcrypt | `bcryptjs` cost 10, จำกัดการเดารหัสผ่าน 5 ครั้ง/15 นาที | ผ่าน (TC-03, TC-04) |
| NFR-04 | รองรับ ≥ 3 อุปกรณ์พร้อมกัน สต็อก/ยอดขายตรงกันภายใน 3 วินาที | หน้า POS ดึงข้อมูลทุก 3 วินาที, การตัดสต็อกใช้ row lock จึงไม่ขายเกินแม้กดพร้อมกัน | ผ่าน (TC-20 ยิง 8 ออเดอร์พร้อมกัน) |
| NFR-05 *(เพิ่มใหม่)* | ความปลอดภัยของข้อมูล | parameterized query ทุกจุด (กัน SQL injection), escape HTML ทุกจุดที่แสดงข้อมูล (กัน XSS), Content-Security-Policy, ไม่เชื่อราคาและรหัสพนักงานจากฝั่ง client | ผ่าน (TC-13, TC-14, TC-44, TC-50) |

```http
  "items": [ { "menuId": 1, "quantity": 2 }, { "menuId": 3, "quantity": 1 } ] }
```

```json
201 Created

400 Bad Request

  "details": { "shortages": [ { "menuId": 6, "name": "โกโก้เย็น", "requested": 1, "available": 0 } ] } }
```

รหัสสถานะที่ใช้: `200` สำเร็จ, `201` สร้างแล้ว, `204` ลบแล้ว, `400` ข้อมูลไม่ถูกต้อง/สต็อกไม่พอ, `401` ยังไม่ login หรือ token หมดอายุ, `403` ไม่มีสิทธิ์, `404` ไม่พบ, `429` เดารหัสผ่านผิดเกินกำหนด, `500` ข้อผิดพลาดของระบบ

**Hardware Interface** — แท็บเล็ต/คอมพิวเตอร์ที่มีเบราว์เซอร์รุ่นใหม่ (Chrome, Safari, Edge) และเครื่องพิมพ์ที่ระบบปฏิบัติการรู้จัก (พิมพ์ใบเสร็จผ่านคำสั่งพิมพ์ของเบราว์เซอร์)

**Communication Interface** — HTTP ภายในเครือข่าย WiFi ของร้าน ข้อมูล JSON (UTF-8) ถ้าเปิดให้เข้าจากนอกร้านต้องใช้ HTTPS

### 3.4 รายงานในระบบ (Report Requirements)

| รายงาน | ผู้ใช้ | ตัวกรอง | ข้อมูลที่แสดง | ประเภท |

กติกาการคำนวณ: นับออเดอร์ที่ `created_at` อยู่ในช่วง `[from 00:00:00, to+1 00:00:00)` ตามเวลาไทย, ยอดขายเมนู = Σ(quantity × unit_price ณ เวลาขาย), เมนูที่ถูกซ่อนแล้วยังนับในรายงาน, เมื่อยอดเท่ากันเรียงตามยอดเงินแล้วตามชื่อเมนู

### 3.5 Data Requirements (Logical Data Model)

ฐานข้อมูล 7 ตาราง (รายละเอียดใน `wk07-schema.sql` และ `wk07-er-diagram.png`)

| ตาราง | เก็บอะไร | กติกาสำคัญ |
|---|---|---|
| `branch` | สาขา | — |
| `category` | หมวดหมู่เมนู | ชื่อห้ามซ้ำ |
| `employee` | พนักงาน + บัญชีผู้ใช้ | `role` ∈ {barista, owner}, `username` ห้ามซ้ำ, รหัสผ่านเป็น bcrypt hash |
| `menu_item` | เมนูของแต่ละสาขา | ราคา ≥ 0, สต็อก ≥ 0, `low_stock_threshold` ≥ 0, `is_active` สำหรับ soft delete |
| `orders` | หัวออเดอร์ | `payment_method` ∈ {cash, transfer, promptpay}, `total_amount` ≥ 0 |
| `order_item` | รายการในออเดอร์ (composition กับ orders) | `quantity` > 0, `unit_price` ≥ 0, ลบ orders แล้วลบตาม (CASCADE) |
| `stock_movement` | ประวัติการเปลี่ยนสต็อก | `reason` ∈ {sale, restock, adjust}, `quantity_change` ≠ 0 |

ความสัมพันธ์: Branch 1–N Employee / MenuItem / Orders, Category 1–N MenuItem, Employee 1–N Orders, Orders 1–N OrderItem, MenuItem 1–N OrderItem / StockMovement, Orders 0..1–N StockMovement
